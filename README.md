> 本教案与投影稿 `slides.md` 章节一一对应。投影负责"看与震撼"，教案负责"讲与组织"。

## 二、教学目标

**知识目标**

- 理解 Git 的三个区域（工作区 / 暂存区 / 本地仓库）与 `commit` 作为"存档点"的含义。
- 掌握回退、分发、协作三类核心命令的用途与区别。

**技能目标**

- 能在 AI 或自己改坏代码后，将项目恢复到上一个可用版本。
- 能把本地仓库推送到远程，并克隆给他人。
- 能使用分支隔离并行修改，独立解决一次合并冲突，并提交 Pull Request。

**态度目标**

- 建立"先存档、再动手"的工程习惯，消除对改坏代码的恐惧。
- 认识到 Git 不是负担，而是让人和 AI 都能放心试错的底层保障。

---

## 三、学情分析（课程切入的四个困境）

学员在学 Git 之前，几乎都踩过下面这几个坑。它们不是危言耸听，而是每天都可能发生的真实场景，也是本课最好的切入点：

| 编号 | 场景 | 学员的真实做法 | 痛点本质 |
| --- | --- | --- | --- |
| ① | 自己写崩 | `main_final_v2.py`、`xxx_别删.zip` | 没有存档点，回不到过去 |
| ② | 被 AI 改崩 | AI 改了十几个文件，程序跑不起来 | 改动不可逆，无法撤销 |
| ③ | 需要分发 | 微信 / 网盘传压缩包 | 压缩包没有历史，也无法同步 |
| ④ | 多人 / 多 AI 协作 | 所有人改同一份文件 | 同一条时间线，互相覆盖 |

**教学决策**：不按"命令手册"的顺序讲，而是按**困境出现的顺序**讲。先让学员感到痛，再给出解法；每讲一个命令，都对应一个刚刚制造出来的问题。

---

## 四、教学重难点

**教学重点**

- `commit` 的心智模型：一次提交 = 一个可以随时回去的存档点。
- 回退四件套的适用场景：`restore` / `reset` / `revert` / `reflog`。
- 分支的意义：用隔离换取并行，用合并换取协作。

**教学难点**

- 暂存区概念抽象，初学者难以理解"为什么要有中间层"。
- `reset` 与 `revert` 的区别、`reset --hard` 的危险性。
- 冲突不是错误而是"需要人来做的选择"这一心态转变。

**突破策略**

- 用"游戏存档"类比三区与 commit。
- 全程用**同一个故事线**贯穿：从崩溃 ① 到崩溃 ④，每一步都在解决上一页留下的问题。
- 冲突部分现场制造、现场解决，不靠背诵。

---

## 五、教学理念与故事主线

**问题驱动（PBL）**：每一幕都是"抛出困境 → 说明旧办法为何失灵 → 引入 Git → 现场演示 → 小结"五段式。

**递进主线**：难度沿"单人单机 → 单人多端 → 多人多端"上升，每一幕恰好弥补上一幕的不足。

```
崩溃①自己写崩 ┐
崩溃②AI 改崩   ┴─> 回退（存档点）
                        │
                        ▼
                  崩溃③分发（压缩包）
                        │
                        ▼
                  远程仓库（clone / push / pull）
                        │
                        ▼
                  崩溃④协作（互相覆盖）
                        │
                        ▼
                  分支 + 合并 + PR（多人 / 多 AI）
```

## 六、课时安排

| 幕 | 主题 | 核心内容 | 时长 |
| --- | --- | --- | --- |
| 第 0 幕 | 导入 | 四个崩溃现场、课程地图、承诺解法 | 3' |
| 第一幕 | 崩溃与回退 | 心智模型、`add/commit`、`restore/reset/revert/reflog`、AI 改崩工作流 | 12' |
| 第二幕 | 分发 | `gh` 建仓 / 克隆、`.gitignore`、GitHub | 8' |
| 第三幕 | 协作 | `branch/switch/merge`、冲突解决、PR、多 AI 工作流 | 12' |
| 收尾 | 总结与作业 | 一句话总结、口头布置课后作业、Q&A | 5' |

**控场提示**

- 时间只有 40 分钟：第一幕是全课地基，若学员卡在"暂存区"就放慢讲透，其余部分按大纲快速带过。
- 每一幕开始前先问一句"这一步你们遇到过吗"，用举手把注意力拉回来。
- 演示务必用同一个仓库贯穿全程：让学员看到 ①→②→③→④ 是同一段故事的延续。
- 手速放慢：命令敲完停一拍，让学员看清输出再解释；不展开额外命令，避免超时。

## 七、逐幕教案

### 第 0 幕 · 导入（3 分钟）

| 环节 | 教师活动 | 学生活动 | 设计意图 |
| --- | --- | --- | --- |
| 提问 | 问："谁丢过代码？谁被 AI 改崩过？" | 举手、共鸣 | 建立共情，降低对 Git 的心理门槛 |
| 立地图 | 展示"四个崩溃现场"，说明本课逐一击破 | 看地图 | 让学员知道痛点和解的对应关系 |

**讲稿要点**：开场不要讲命令。先讲一个几乎人人都经历过的场景——熬夜写崩、被 AI 改崩、传压缩包、多人互相覆盖。然后给出承诺："这四个崩溃现场，Git 都能救。"语气是共鸣与安抚，而不是吓唬。

---

### 第一幕 · 崩溃与回退（12 分钟）

**教学目标**：理解存档点模型；能把项目回退到任意历史版本。

**场景与痛点**

- 崩溃 ①：满目录的 `main_最终版_v2.py`，不知道哪个能跑。
- 崩溃 ②（重点）：AI 一次改了 12 个文件，项目直接跑不起来，编辑器已保存，原代码没了。

**知识点**：工作区 / 暂存区 / 本地仓库；`init`、`add`、`commit`、`log`；`restore`、`reset`、`revert`、`reflog`。

**演示步骤（建议顺序）**

1. 展示"文件名版本管理"的目录，制造混乱感。
2. `git init` → `git add .` → `git commit -m "能跑的版本"`，强调"这就是存档"。
3. 改坏一个文件，直接 `git restore .` 瞬间恢复。
4. 让 AI 动手重构：
   - 动手前：`git commit -m "AI 重构前的稳定版本"`（**全课最重要的习惯**）。
   - 改崩了：`git restore .` 全丢弃；若已提交：`git reset --hard HEAD~1`。
5. 演示 `git reflog`，把 reset 掉的提交找回来，制造"终极后悔药"的高潮。

**教师活动 / 学生活动**

| 教师 | 学生 |
| --- | --- |
| 边讲边敲，故意改崩再救回 | 同步在本地敲一遍 |
| 强调 `reset --hard` 危险、`revert` 安全 | 记录两条命令的差别 |

**设计意图**：把最抽象的三区概念，用"存档 → 改坏 → 读档"的即时反馈讲清楚。AI 改崩场景让 Git 从"课程内容"变成"生存技能"。

**对应投影**：`崩溃现场`、`Git 的心智模型`、`让 AI 动手之前，先存档`（magic-move 动画）、`改崩了怎么办`。

---

### 第二幕 · 分发（8 分钟）

**教学目标**：能把仓库推送到远程，并克隆给他人。

**场景与痛点**：崩溃 ③——用微信 / 网盘传压缩包的三种翻车现场：文件太大、传到一半、两边都改了。

**知识点**：`gh repo create` / `gh repo clone`、`push`、`pull`、`.gitignore`；用 GitHub 托管仓库。

**演示步骤**

1. 现场把一个仓库用压缩包"分发"，展示信息丢失（没有历史、无法同步）。
2. 用 gh 一键建仓并推送：`gh repo create git-slides --public --source=. --push`（首次先 `gh auth login`）。
3. 在另一个目录 `gh repo clone <owner>/git-slides`，展示"完整历史"一起被复制。
4. 改一处 → `git push` → 另一侧 `git pull`，演示同步。
5. 讲 `.gitignore`：演示误传 `node_modules` / `.env` / 密钥的后果。

**设计意图**：让学员看到"远程仓库 = 带历史的云端副本"，而不是又一个网盘。

**对应投影**：`崩溃现场：分发`、`第二幕解法：远程仓库`。

---

### 第三幕 · 协作（12 分钟）

**教学目标**：能用分支隔离并行修改，能独立解决一次冲突，理解 PR 与多 AI 工作流。

**场景与痛点**：崩溃 ④——你改 A 文件、队友改 B 文件结果互相覆盖；两个 AI 并行改同一份代码，谁也合不进去。

**知识点**：`branch`、`switch`、`merge`、冲突标记与解决、Pull Request、多 AI 协作工作流。

**演示步骤**

1. 抛问题："所有人挤在同一条时间线上会怎样？"然后现场制造一次覆盖。
2. 引出分支：`git switch -c feature/login`，配合 `GitGraph` 动画展示主线分叉、AI 分支、合并。
3. 制造并解决一次冲突：
   - 展示 `<<<<<<<` / `=======` / `>>>>>>>` 标记。
   - 手动选择保留哪边，删掉标记，`git add` → `git commit`。
   - 强调："冲突不是错误，是 Git 把选择权交还给你。"
4. 讲 PR：合并前先审查改动、留记录、跑测试再合。
5. 延伸到多 AI 工作流：每个 AI / 每个任务各开分支 → 改完开 PR → review 后合并。避免 AI 互相覆盖。

**设计意图**：把"协作"从口头约定升级为工程流程。多 AI 场景是面向未来的增量，直接回应"AI 时代为什么还要学 Git"。

**对应投影**：`崩溃现场：协作`、`第三幕解法：分支`（GitGraph 自动播放）、`冲突：不是错误，是选择`、`多 AI 协作：分支 + PR`。

---

### 收尾 · 总结与练习（5 分钟）

**一句话总结**：先 `commit`，再动手——无论动手的是你还是 AI；用远程分发，用分支协作；只要能回退，你就永远不会真的崩溃。

**对应投影**：`一句话总结`、`Q & A`。

## 八、演示环境准备

- [ ] 一个干净的演示仓库，预置"能跑的版本"以便随时改崩。
- [ ] 幻灯片本地启动：`npm run dev`；投屏前用浏览器全屏，按 `o` 可预览总览。
- [ ] GitHub 账号已登录（`gh auth status` 显示已登录），仓库名预留好。
- [ ] 若现场演示 AI 改代码，提前准备好"会被改崩"的具体指令，避免临场翻车。
- [ ] 断网预案：提前把远程仓库操作录屏，或用本地裸仓库模拟远程。
- [ ] 备用终端字号调大，确保后排能看清命令输出。

## 十、课后作业（口头布置，无投影页）

1. 建一个仓库，提交三次，用 `git log` 与 `git reflog` 各回退一次并说明差异。
2. 故意让 AI 改崩一次，用 `git restore .` 救回来。
3. 推送到 GitHub，再 `clone` 到另一个目录，模拟一次"分发"与"同步"。
4. 开两条分支修改同一行，制造冲突并解决，然后开一个 Pull Request。

## 十一、常见问题与坑

| 问题 | 说明 |
| --- | --- |
| `reset --hard` 会不会丢代码？ | 会。未提交的改动不可恢复；已提交的可用 `reflog` 找回。 |
| `reset` 和 `revert` 怎么选？ | 本地未推送用 `reset`；已推送、多人共用用 `revert`。 |
| 为什么先 `add` 再 `commit`？ | 暂存区让你挑选本次要存档的改动，而不是一股脑全存。 |
| `.env` / 密钥误提交了怎么办？ | 立刻更换密钥；用 `.gitignore` 防再犯；必要时清理历史。 |
| 分支太多会乱吗？ | 分支便宜且轻量；真正要治理的是"合并前的 review"。 |
